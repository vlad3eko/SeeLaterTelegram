# Задачи проекта «Киноманов» (SeeLaterTelegram)

Файл для контекста. Claude читает его в начале работы и обновляет после каждой заметной правки, чтобы задачи не терялись, когда разговор сжимается. Секретов здесь нет и быть не должно.

Обновлено: 24.11.2026 МСК. Файл почищен: выполненное и журналы работ убраны (история — в git), референсы и решения по формату Reel — в `docs/reel-format.md`. План этапа 2 и задачи ведутся также в MARS (план «Этап 2. Выбор фрагментов из длинного видео»).

## Как устроено (коротко)

- Сайт и бот: Nuxt 4 / Nitro на Vercel. Бот «Киноманов BOT» работает через webhook с секретом.
- Reels: Vercel ставит задачу в `reel_processing_jobs` (`dispatchReelJob`) и запускает Cloud Run Job `kinomanov-reel-worker` (проект `kinomanov-reels-worker`, регион `europe-west3`, task-timeout 1800 с).
- Кнопка «Загрузка трейлера» (режим `download`) только скачивает трейлер и присылает его в чат, Reel не собирает. С 19.11 скачивает воркер Cloud Run (`jobs/trailerDelivery.ts`, `workers/reel-worker/src/trailerDelivery.ts`): Vercel запускает его, готовый файл приходит через временную папку R2 на `/api/bot/trailerDelivery` и пересылается в чат потоком. На Vercel нет ни yt-dlp, ни bgutil (сервис `bgutil-next` удалён) — экономия Active CPU.
- Воркер (`workers/reel-worker/src/index.ts`): `prepareReel` → скачивание трейлера, clean-видео 40 с, хук от Gemini, субтитры (Gemini + Whisper), оформление → `ready` → финализатор на Vercel публикует в Telegram и Instagram.
- Фрагмент 40 с выбирается эвристикой в `prepareInstagramVideo.ts` (середина трейлера минус 10 с) прямо из полного трейлера. `trimVideo.ts` нигде не импортируется (проверено по импортам 11.11), файл можно удалить.
- Если Reel не удался, финализатор публикует только в Telegram (`published_telegram_only`).
- **Одна запись на фильм** в `reel_processing_jobs`: уникальный ключ `(media_id, media_type)`, таблица не история публикаций. Повторное нажатие «Опубликовать»:
  - задача в работе, или публикация упала на середине (`telegram_pending`, `telegram_published`, `instagram_container_created`, `instagram_published`), или тот же update пришёл повторно: продолжается существующая запись, ничего не удаляется;
  - иначе (фильм опубликован, Reel не получился, воркер упал до публикации): старая запись удаляется и создаётся новая, с новым хуком, описанием, токеном и данными нажатия. Ничего из старой записи не переносится;
  - одно исключение: если пост в канал уже вышел (`published_telegram_only`), в новую запись копируется `channel_message_id`, и карточка в канал второй раз не уходит. После полной публикации новая карточка в канал уходит;
  - трейлер повторно не скачивается, если ключ `key_trailer` тот же: clean-видео лежит в R2 по пути `instagram/reels/clean/{id}_{type}_{key}_clean.mp4` и берётся оттуда (в логе `[REEL CLEAN CACHE HIT]`). С другим ключом путь другой, всё делается заново. Файлы старого ключа в R2 остаются (чистки пока нет).

## План: этап 2 — выбор фрагментов из длинного видео (цель 5)

Цель владельца: из исходника 6–10 минут (нарезка по фильму с YouTube, одна ситуация) код сам выбирает несколько фрагментов с общей линией повествования и собирает ролик 60–90 с в формате 1:1 (хук-подложка, субтитры, «Сохрани…»). Интерфейсы не привязывать к длине исходника. Референс, формула и замеры — `docs/reel-format.md`. Архитектура — черновик, согласовать с владельцем до реализации.

Черновик архитектуры:

- Три контракта, не зависящих от длины исходника: (1) индекс исходника: видео, список планов (детектор склеек), при необходимости слова с таймингами; (2) `selectStory(индекс, целевая длина)` возвращает список отрезков `{начало, конец, роль, почему}`, текст хука и длину подложки; (3) `renderEdl(список, исходник)` собирает clean 1:1 и не знает, откуда взялся список.
- Для исходника до 10 минут выбор делается одним запросом к Gemini по видео целиком (около 100 токенов в секунду видео на низком разрешении, порядка 60 тысяч токенов). Для фильма на 2 часа меняется только внутренность `selectStory` (проход кусками по ~10 минут с кандидатами, затем общий выбор), контракты и сборка те же.
- Whisper не гонять по всему исходнику: Gemini даёт приблизительные границы, код подгоняет их к границам планов, затем Whisper запускается только на выбранные отрезки с запасом по краям, чтобы довести границы до слов и получить субтитры.
- Нарезка сразу в нужное качество: вырезать только выбранные отрезки (по `-ss` и `-t`), а не перекодировать весь исходник; учесть таймаут задачи Cloud Run 1800 с и скачивание 4K на 10 минут.
- Кроп (чёрные полосы) определять один раз на исходник по нескольким пробам с разных мест, брать самое частое значение; заставку и чёрные кадры в начале и конце в пробы не брать. Одна проба на отрезок даёт ошибки на тёмных сценах (см. «Что выяснено 11.11»).
- Хук пишется после выбора фрагментов, по исходу истории (формула, цель 5).
- Режим «в тени» на первых запусках: ничего не публикуем, список отрезков и пробный рендер кладём локально через стенд.
- Идеи из `browser-use/video-use` (10.11) сюда же: `Timeline Analyzer` ≈ индекс исходника, `Clip Selector` ≈ `selectStory`, `ReelQualityGate` — проверка результата. Не переносить: Scribe, `render.py`, `grade.py`, автонормализацию звука.

Задачи (подробно — в MARS):
1. Согласовать архитектуру и контракты с владельцем.
2. Индекс исходника: планы (scdet), полосы по нескольким пробам, исключение заставки и чёрных кадров.
3. `selectStory`: запрос к Gemini по видео целиком, схема отрезков с ролями, проверка ответа.
4. `renderEdl`: нарезка отрезков, подгонка к склейкам и словам (Whisper только по выбранному), кроссфейд звука, clean 1:1.
5. Хук по исходу истории и проверка отрезков на жестокие сцены.
6. Режим «в тени»: стенд локально, список отрезков и пробный рендер для владельца.

Открытые вопросы: что считать «интересным фрагментом» (эмоция, диалог, действие, законченность сцены); коэффициент подложки хука (≈6 % длины, 4–10 с) проверить на тестах.

## Доработки текущего Reel

1. Детектор фигуры человека для планов без лица (тест 4: ребёнок в профиль, темно).
2. Выбор говорящего, когда в кадре два лица (сейчас берётся самое крупное).
3. Приёмка: стенд на 3–4 трейлерах (светлый, тёмный, 2,39:1, лицо у верхнего края), скриншоты на ПК и телефоне; после перезаписи по тем же путям R2 по ссылке отдаётся новый файл.
4. Чистка R2: файлы старых ключей `key_trailer` (`clean/`, `reel/`) не удаляются.

## Отложено (без плана)

- Уведомления, второй этап: кнопка «🔕/🔔 Обновления» в карточке (`favorites.notifications_enabled`), `users.digest_silent` → `disable_notification`, метрики (запросы TMDB в сутки, событий на сводку), цифровой релиз отдельным событием.
- `/g`: «Собрать карусель» из подборки (сейчас заглушка для админа) и публикация в Instagram / Threads / Facebook, общее видео из трейлеров.
- Сайт: вход по токену `commandStart` (находки 8, 9 аудита Instagram 23.11); ручная привязка фильма к Reel по TMDB id.

## Решения и риски

- Время сборки Reel в функции Vercel: снято 11.11 16:38. Режим `download` Reel больше не собирает, только скачивает трейлер и отправляет его в Telegram (см. выше), поэтому лимит `maxDuration` 300 с ему не грозит. Реальное время функции (скачивание ≤1080p, возможное сжатие больше 45 МБ) стоит один раз глянуть в логах Vercel.
- Кэш clean в R2 фиксирует качество: clean, собранный один раз (в том числе из 360p в неудачную сессию YouTube до правки 11.11), переиспользуется при каждой публикации того же `key_trailer`, пока файл не удалят из R2. Кэш сам не сбрасывается (решение владельца). Clean, который раньше собрал режим `download` на Vercel, тоже лежит в R2 и будет переиспользован воркером; новых таких clean больше не появится. Старые clean в вертикальном макете пересобираются сами (`CHECK_CLEAN_LAYOUT`).

## Памятка: выкатка и настройки

Коммит и сборка воркера (тег увеличивать при каждой сборке):

```
git add -A
git commit -m "..."
git push
node scripts/prepareReelWorkerBuildContext.mjs
gcloud builds submit .cloud-run-build/reel-worker --tag europe-west3-docker.pkg.dev/kinomanov-reels-worker/kinomanov-workers/reel-worker:<тег> --machine-type e2-highcpu-8 --timeout 3600s
gcloud run jobs update kinomanov-reel-worker --region europe-west3 --image europe-west3-docker.pkg.dev/kinomanov-reels-worker/kinomanov-workers/reel-worker:<тег> --cpu 4 --memory 8Gi --task-timeout 1800s
```

Переменные Cloud Run Job (все необязательные, указаны значения по умолчанию):

| `REEL_SUBTITLE_WHISPER_TIMEOUT_MS` | 6 мин | Лимит одного прохода Whisper |
| `REEL_SUBTITLE_TRANSLATE_RESERVE_MS` | 240 с | Время, которое бережётся для перевода |
| `REEL_SUBTITLE_TRANSLATE_REQUEST_TIMEOUT_MS` | 25 с | Лимит одного запроса перевода |
| `REEL_SUBTITLE_TRANSLATE_MODEL` / `..._FALLBACK_MODEL` | `gemini-3.8-flash` / `gemini-3.5-flash-lite,gemini-3.5-flash,gemini-3.7-flash,gemini-2.5-flash` (через запятую) | Цепочка моделей перевода; круги с паузами 5/15/30/60 с, у 429 — пауза из ответа |

Локальный сухой прогон публикации (без Cloud Run, R2 и Instagram), запуск из корня проекта в терминале IDE. На Windows и macOS один раз (и при смене версии yt-dlp) нужен `npm run reel:setup-ytdlp`: он ставит yt-dlp и плагин BGUtil в `tmp/tools` (в `.gitignore`). Версия yt-dlp в скрипте `scripts/setupLocalYtDlp.mjs` должна совпадать с `scripts/prepareMediaTools.mjs`. После прогона локальный BGUtil-сервер (порт 4416) остаётся запущенным и подхватывается следующим запуском.

```
npm run reel:dryrun -- --key <id трейлера на YouTube> --title "Название" --genre "Ужасы, Триллер" --rating 7.4 --release 2026-05-14
```

Все параметры и описание файлов результата: комментарий в начале `server/global/engine/instagram/reel/scripts/dryrun-publish.ts`. Результат в `tmp/dryrun/<имя запуска>/`: `reel.mp4`, `clean.mp4`, `caption.txt`, `instagram-request.json`, кадры, `run.log` (весь вывод терминала), `summary.json` (в нём `source`: какой формат YouTube скачан, `encoded`: профиль, fps и битрейт clean и reel, `transcription`: чем распознавали речь и сколько слов услышал каждый), папка `subtitles/` с `transcript.txt`. Параметры транскрипции: `--transcription gemini|whisper` (по умолчанию gemini), `--gemini-timing whisper|gemini`, `--whisper-fallback`. По умолчанию хранилище `tmp/dryrun/storage` очищается перед запуском, чтобы изменения монтажа не скрывал кэш clean; `--reuse` оставляет его.

| Переменная | Где ставится | Что делает |
| --- | --- | --- |
| `REEL_LOCAL_STORAGE_DIR` | скрипт сухого прогона | Вместо Cloudflare R2 файлы лежат в этой папке, ссылки вида `file:///...`. В Vercel и Cloud Run (`VERCEL`, `CLOUD_RUN_JOB`, `K_SERVICE`) модуль выбросит ошибку при загрузке |
| `INSTAGRAM_DRY_RUN` | скрипт сухого прогона | `true`: `publishInstagramReel` ничего не отправляет, а пишет `reel.mp4`, `caption.txt`, `instagram-request.json`. Коллбэки не вызываются. В Vercel и Cloud Run запрещено |
| `INSTAGRAM_DRY_RUN_DIR` | скрипт сухого прогона | Папка для этих файлов; без неё `tmp/instagram-dry-run/<время>` |

Секреты из `.env` подхватываются через `--env-file=.env`. Сам скрипт и сухая публикация значения токенов не выводят (проверка окружения показывает только «задан / не задан»).
