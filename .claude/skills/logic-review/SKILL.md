# Логический аудит от лица пользователя

Задача — найти места, где программа ведёт себя не так, как ожидает человек: теряет действие, делает его дважды,
застревает, противоречит сама себе, пишет одно, а делает другое, пускает туда, куда не должна, или молча ничего не делает.
Типы, синтаксис и тесты — НЕ сюда (это telegram-test / tsc). Отвечай по-русски.

**Ничего не меняй.** Не правь файлы, не коммить, не применяй миграции. Не запускай то, что пишет в базу, шлёт сообщения
людям, публикует или дёргает таймеры и очереди. Можно: git (только чтение), поиск, чтение кода и документации, чтение
схемы миграций. Итог — только отчёт; исправления делаются потом, отдельно и по решению владельца.

## 1. Режим

Аргументы вызова: `$ARGUMENTS`.

Если в них уже ясно, что проверять (файл, папка, функция, фича, коммит, «всё»), — не спрашивай. Иначе один вопрос
через AskUserQuestion (заголовок «Охват»):

| Вариант | Что проверяется |
|---|---|
| Последние изменения (рекомендуется) | незакоммиченное + коммиты, которых нет в основной ветке; если их нет — последний коммит |
| Конкретный участок | фича, экран, команда или папка — человек назовёт в «Other» или следующим сообщением |
| Диапазон коммитов | `A..B`, ветка или «за N дней» |
| Полный аудит | вся программа: карта функций → проход по каждой |

Второй вопрос (заголовок «Глубина») — только если охват большой (полный аудит или больше ~15 изменённых файлов):
«Быстро — главные пути и явные дыры» / «Тщательно — все ветки и крайние случаи».

## 2. Понять проект (коротко, один раз)

Прочитай `CLAUDE.md` / `AGENTS.md` / `README` и журнал проекта, если он есть (`TASKS.md`, `CHANGELOG`…): кто
пользователи (люди, администратор, внешние сервисы, таймеры), где точки входа (команды, кнопки, роуты, страницы,
вебхуки, крон, очереди), какие решения владельца уже приняты — **принятое решение не дыра**, но расхождение кода с
ним — дыра. Не перечитывай то, что уже есть в контексте разговора.

## 3. Что изменилось

- Основная ветка: `git symbolic-ref refs/remotes/origin/HEAD` (иначе `main`/`master`).
- Последние изменения: `git status --short`, `git diff`, `git diff --cached`, `git log --oneline <основная>..HEAD`
  и `git diff <основная>...HEAD`; пусто → `git show --stat HEAD` и `git show HEAD`.
- Диапазон: `git log --oneline A..B`, `git diff A..B`.
- Читай сообщения коммитов: в них заявлено намерение — сверяй код с ним.
- Участок / полный аудит: изменения не нужны; для полного — составь карту функций (по точкам входа), 5–20 пунктов.

Для каждого изменения запиши одной строкой: **что теперь должно происходить для человека** (намерение).

## 4. Цепочки

Для каждой изменённой единицы (функция, обработчик, запрос, таблица, текст) найди:
- **вверх** — все пути от действий человека до неё: кто вызывает, через какие кнопки/команды/роуты/таймеры
  (поиск использований имени, роута, ключа, текста; обязательно — второстепенные входы: повтор, deep link, старая кнопка
  в истории чата, админ-путь, ретрай очереди);
- **вниз** — что она меняет: записи в базе, сообщения, состояние сессии, кэши, файлы, внешние вызовы — и кто потом
  читает это состояние.

Цепочка = вход → шаги → видимый результат + оставшееся состояние. Изменение в общей функции проверяй во **всех**
её цепочках, не только в той, ради которой её меняли.

Большой охват (полный аудит, много цепочек): раздай независимые цепочки или области субагентам Explore (только чтение)
параллельно, каждому — цепочку, намерение и список вопросов ниже; от них нужны находки в формате отчёта, не пересказ кода.
Каждую находку субагента перед отчётом проверь сам по коду.

## 5. Пройти как пользователь

Для каждой цепочки мысленно пройди её **по коду** (а не по описанию) как конкретный человек и задай вопросы:

**Кто**
- новый человек (нет строки в базе, не запускал бота/не логинился) · вернувшийся (старые данные до миграции, старый формат)
- без нужных прав / подписки / оплаты · заблокировал бота или отписался посреди пути · администратор · чужой (взял чужую ссылку/токен)

**Порядок и повторы**
- нажал дважды / быстро подряд / из двух устройств · вернулся назад и нажал старую кнопку · прервался на середине и
  пришёл через день · сделал шаги не по порядку · пропустил шаг · повторил уже выполненное

**Данные**
- пусто / ничего не найдено / одна запись / очень много · длинный текст, эмодзи, другой язык · ноль, отрицательное,
  дробное · фильм vs сериал (и любые другие «два похожих типа»), одинаковые id разных типов · удалённая/скрытая сущность

**Время и среда**
- полночь, смена дня, часовой пояс (время продукта), истёкший срок (TTL, токен, кэш) · лимиты платформы (длина
  сообщения, размер кнопки, частота) · таймаут функции посреди работы · два параллельных запуска таймера/воркера

**Сбои**
- внешний сервис ответил ошибкой/медленно/пусто · запись в базу прошла наполовину · таблицы/колонки ещё нет
  (миграция не применена) · сообщение не доставилось — что осталось в состоянии и что увидит человек при повторе

**Слова и обещания**
- текст сообщения, кнопки, подсказки совпадает с тем, что реально произойдёт? обещанное («напомню», «сохранится само»)
  действительно где-то выполняется? человек понимает, что делать дальше, или упирается в тупик без кнопки?

**Согласованность**
- тот же сценарий через другой вход ведёт себя так же? счётчики, статусы, флаги снимаются там, где ставятся?
  есть ли состояние, из которого нет выхода?

Находка засчитывается, только если ты прошёл путь по коду до конкретной строки. Догадку без пути — в «Проверить вручную».

## 6. Отчёт

Сначала одна строка: охват (режим, какие коммиты/файлы/области), сколько цепочек пройдено.

Затем находки, самые серьёзные первыми, каждая так:

```
### N. <суть одной фразой>  — [критично | важно | мелочь]   (уверенность: подтверждено кодом | вероятно)
Кто и что делает: <человек и его шаги, 2–4 шага>
Ожидает: <что он думает, что будет>
Происходит: <что делает код> — `путь/файл.ts:строка` (и другие звенья цепочки)
Почему: <звено, где логика рвётся>
Направление исправления: <1–2 фразы, без кода>
```

Серьёзность: **критично** — потеря/порча данных, двойное действие с последствиями (двойная отправка, двойное списание),
доступ не тому, человек застревает без выхода; **важно** — действие не выполняется или выполняется не так в заметном
сценарии, вводящий в заблуждение текст; **мелочь** — редкий крайний случай, косметика поведения.

В конце:
- **Проверить вручную** — что не удалось подтвердить чтением (зависит от внешнего сервиса, данных в базе, настроек),
  и как проверить;
- **Пройдено без замечаний** — цепочки списком в одну строку каждая (чтобы было видно, что проверено);
- **Не проверялось** — что осталось за охватом.

Не пересказывай код и не перечисляй, что «хорошо сделано». Не предлагай рефакторинг ради стиля. Если находок нет —
так и скажи, с перечнем пройденных цепочек.
